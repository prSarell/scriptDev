# Gaffer fits downstream of Maya, not inside it

Gaffer is a free, BSD-licensed node-graph application for lookdev, lighting and automation. It works the way Katana does, and RMIT can adopt it without per-seat software cost. It has to sit **downstream of Maya as a separate, file-fed stage**: there is no live bridge, it runs its own Python and its own USD, and Arnold has to be pointed at it separately. The current release is **1.7.7.0 (2026-11-12)**, the build the studio has already downloaded. It ships an official Windows build, bundles Cycles, and supports **Arnold 7.4 and 7.5**. That lines up with this machine's Maya 2027 MtoA, which a local check shows runs **Arnold 7.5.2.0**. Four things decide how hard integration will be. First, Gaffer bundles **Python 3.11** while Maya 2027 runs **3.13.9**, so shared pipe modules must stay importable under both. Second, Gaffer needs a **standalone Arnold SDK**, because the MtoA folder layout probably fails its version check. Third, SceneReader **flattens USD composition**: variants, payloads and layer structure don't survive as editable things. Fourth, Arnold licensing for a third-party host on lab machines is **undocumented** by Autodesk. Gaffer's strengths line up well with the pipe as it stands. The pipe already publishes model USD, caches animation as Alembic and has a custom render service, and Gaffer offers non-destructive "read then tweak" lookdev on published USD, first-class render passes, and a simple `gaffer execute` command line that the Scout render manager can drive directly. There is no school precedent and little current teaching material, so the curriculum would be RMIT's to write.

## A one-studio-group project with a fast, two-branch release train

John Haddon started Gaffer on his own in 2007. It was open-sourced in 2011 and has been "used and extended in production" at Image Engine ever since. It is built on Cortex, Image Engine's library of VFX data types ([Post Magazine, 2017](https://postmagazine.com/Publications/Post-Magazine/2017/February-1-2017/Workflow-Image-Engines-open-source-VFX-tools.aspx)). Image Engine partnered with Cinesite in **July 2015** and now sits in the Cinesite group with Trixter and L'Atelier Animation ([Wikipedia](https://en.wikipedia.org/wiki/Image_Engine)). Cinesite says the group "fully develops and supports" Gaffer for both VFX and feature animation ([Cinesite](https://cinesite.com/technology/)). Copyright is held jointly by Haddon, Image Engine and Cinesite. The licence is **BSD-3-Clause**, and the code lives at GafferHQ/gaffer: about 24,000 commits and 1.1k stars as of November 2026 ([GitHub](https://github.com/GafferHQ/gaffer)). No governance charter, technical steering committee or Academy Software Foundation (ASWF) membership could be found. In practice Gaffer is in-house studio R&D released in the open, and a small core team tags the releases. That carries two risks. The roadmap follows Cinesite's needs, not a school's. On the other hand, the project is well funded and actively developed. No paid support contract exists.

The release history is regular. **1.0.0.0 shipped 2022-07-06**, and since then about one major version has landed per year: 1.4 in April 2024, 1.5 in October 2024, 1.6 in August 2025 and **1.7.0.0 on 2026-08-13**. Point releases follow every one to three weeks, and the **1.6 line is still patched in parallel** (1.6.21.8 shipped the same day as 1.7.7.0) ([GitHub Releases API](https://api.github.com/repos/GafferHQ/gaffer/releases)). Version numbers have four parts, MILESTONE.MAJOR.MINOR.PATCH, and breaking changes land only in x.Y.0.0 releases. Each of those has a "Breaking Changes" section ([Changes.md](https://github.com/GafferHQ/gaffer/blob/main/Changes.md)). The project targets the **CY2025 VFX Reference Platform** ([README](https://github.com/GafferHQ/gaffer)). 1.7 bundles Python 3.11.14, Qt/PySide 6.5.8, USD 26.05, OCIO 2.4.2, MaterialX 1.39.4, OSL 1.14.8 and Cycles 5.1.0. The unreleased next major (presumably 1.8) already moves to **Python 3.13.16 and Qt 6.8.5** ([Changes.md](https://github.com/GafferHQ/gaffer/blob/main/Changes.md)). Its dependency alphas move to USD 26.11.1 and MaterialX 1.39.5 ([GafferHQ/dependencies](https://github.com/GafferHQ/dependencies/releases)). For a teaching year this cadence is useful. RMIT can **pin one major version for the March 2027 intake**, take only patch releases, and treat the next major as a deliberate summer upgrade. Patch releases are not risk-free, though: 1.6.21.2 had to fix a crash introduced by Arnold 7.5.2's change to the `driver_exr` compression parameter ([Changes.md](https://github.com/GafferHQ/gaffer/blob/main/Changes.md)).

## The lazy, hash-cached scene graph is the main thing to learn

Gaffer's core is a C++ and Python graph of nodes and plugs. Nothing is computed until something asks for it. A ComputeNode first hashes every input and context variable that affects its output, then uses that hash as a key into a thread-safe in-memory cache ([ComputeNode.h](https://github.com/GafferHQ/gaffer/blob/main/include/Gaffer/ComputeNode.h)). A **Context** carries the variables for each request (frame, scene location, image tile and so on). Contexts flow upstream while data flows downstream, and each thread has its own ([Contexts doc](https://github.com/GafferHQ/gaffer/blob/main/doc/source/WorkingWithTheNodeGraph/Contexts/index.md)). A scene is not a loaded blob. It is a hierarchy of *locations* such as `/world/city/building01`, and each location's transform, bound, object and inherited attributes are computed independently and on demand ([Anatomy of a Scene](https://github.com/GafferHQ/gaffer/blob/main/doc/source/WorkingWithScenes/AnatomyOfAScene/index.md)). Images work the same way, as 32-bit float, 128×128 tiles computed per channel ([Anatomy of an Image](https://github.com/GafferHQ/gaffer/blob/main/doc/source/WorkingWithImages/AnatomyOfAnImage/index.md)). The docs warn Maya users directly that Gaffer's "attributes" are not Maya's attributes: the Maya equivalent is a **plug**. Render options and outputs play the part of Maya's render globals. Cost scales roughly with locations × nodes, so the docs recommend applying lookdev per asset before grouping, and warn that `/.../` wildcards in Prune or Isolate are the worst case ([Performance Best Practices](https://github.com/GafferHQ/gaffer/blob/main/doc/source/WorkingWithTheNodeGraph/PerformanceBestPractices/index.md)). This is the main change in thinking for Maya-trained students. Maya mutates a scene in place; Gaffer builds a recipe that is re-evaluated on every request.

### Lookdev and lighting are mature, but there are no templates

Lookdev in Gaffer means "read, assign, tweak". Shader nodes include ArnoldShader, OSLShader, CyclesShader, RenderManShader and USDShader. ShaderAssignment binds them to locations through PathFilters or set expressions. ShaderTweaks, AttributeTweaks and EditScopes change anything upstream without touching the source file ([GafferScene headers](https://github.com/GafferHQ/gaffer/tree/1.7.7.0/include/GafferScene); [GafferArnold headers](https://github.com/GafferHQ/gaffer/tree/1.7.7.0/include/GafferArnold)). The editor set has been built up steadily since 2022:

| Editor | Added in |
|---|---|
| Light Editor | 0.61.2 (2022) |
| Set Editor | 1.2.1 |
| Render Pass Editor | 1.3.11 (Jan 2024) |
| Attribute Editor | 1.5.0 (Oct 2024) |
| Light Linking Editor | 1.7.0 (Aug 2026) |

Arnold, Cycles and 3Delight can all render live in the Viewer ([Changes.md](https://github.com/GafferHQ/gaffer/blob/main/Changes.md)). Lighting covers renderer-specific lights and renderer-agnostic USDLux lights, Arnold blockers, gobos and barndoors, mesh lights, attribute-based light and shadow linking, a manipulator LightTool, and **first-class render passes**. The RenderPasses node (1.3.8) stores pass names in an option that dispatch can iterate over. Arnold has written multi-layer EXRs since 1.6, with a `layerPerLightGroup` output option since 1.7.3 ([Changes.md](https://github.com/GafferHQ/gaffer/blob/main/Changes.md)). Renders stream into a **Catalogue** node, a snapshot history that is itself a node. Lighters can grade, comp or build contact sheets straight from it, using GafferImage's Merge, Grade, OCIO, deep and multi-view nodes ([CatalogueUI.py](https://github.com/GafferHQ/gaffer/blob/1.7.7.0/python/GafferSceneUI/CatalogueUI.py)). Some things are missing. There is no built-in lookdev or turntable template, no material-library browser, and no MaterialX authoring node. MaterialX ships only as a library dependency ([include/ @1.7.7.0](https://github.com/GafferHQ/gaffer/tree/1.7.7.0/include)). The default OCIO config is still **ACES 1.3**, because RenderMan doesn't support ACES 2.0 ([Changes.md](https://github.com/GafferHQ/gaffer/blob/main/Changes.md)). Gaffer and MtoA renders will only match if both apps load the same OCIO config and view. RMIT would have to build the turntable rig, light rigs and shader presets itself, as Box or Reference files.

### Four renderers, one of them bundled

Gaffer 1.7 supports Arnold 7.4/7.5 (via `ARNOLD_ROOT`), **Cycles 5.1 (bundled, CPU and CUDA/OptiX GPU)**, 3Delight (via `DELIGHT`) and RenderMan 27.x (via `RMANTREE`). Appleseed was dropped in 1.3 ([third-party config doc](https://github.com/GafferHQ/gaffer/blob/1.7.7.0/doc/source/GettingStarted/ConfiguringGafferForThirdPartyTools/index.md); [download page](https://www.gafferhq.org/download/)). On Windows, 3Delight's lights and shaders require 3Delight for Maya to be part of the install. RenderMan 26.4 is unavailable on Windows ([Changes.md](https://github.com/GafferHQ/gaffer/blob/main/Changes.md)). The local inspection of the downloaded zip confirms this: it contains `arnold/7.4/` and `arnold/7.5/` modules, a bundled `cycles/` folder and a `renderMan/` folder, and **no Arnold binaries**. For a school, the bundled Cycles is a real fallback. If Arnold licensing for Gaffer is late or blocked, students can still learn the whole lookdev and lighting workflow with no licence server, and the official GafferBot tutorial itself uses Cycles ([GafferBot tutorial](https://www.gafferhq.org/documentation/1.7.6.0/GettingStarted/TutorialAssemblingTheGafferBot/index.html)).

## USD arrives flattened, and Maya hands off through files only

Gaffer reads and writes USD through Cortex's IECoreUSD. **SceneReader composes the stage and converts it into Gaffer locations**, and once a file is loaded its references and layers are no longer visible as composition ([gaffer-dev thread](https://groups.google.com/g/gaffer-dev/c/btfWzh2szwk)). A lot is supported: UsdShade bindings, including purpose-based ones; `usd:purpose` filtering and Viewer presets; `kind`-aware selection; UsdLux for all renderers; UsdPreviewSurface translated at render time for Arnold, Cycles, 3Delight and RenderMan; UsdSkel, baked into the mesh on load; USD volumes; PointInstancers; and in-memory stages through `stageCache:` ([Changes.md](https://github.com/GafferHQ/gaffer/blob/main/Changes.md); [Cortex Changes](https://github.com/ImageEngine/cortex/blob/main/Changes)). For writing back out, SceneWriter writes a flattened file, and **USDLayerWriter bakes just the difference between two Gaffer scenes into a minimal USD layer**. That is the realistic way to hand lookdev or light edits to other applications as an overlay ([Changes.md](https://github.com/GafferHQ/gaffer/blob/main/Changes.md)). The research found nothing at all on **variant selection or payload control**: issue searches for "variant" and "payload" returned nothing relevant. Gaffer sees whatever variant selections are authored in the file, so switching variants needs an upstream layer or a separate SceneReader per variant. There is also no Gaffer documentation on custom asset resolvers. An ArResolver built against USD 26.05 and put on `PXR_PLUGINPATH_NAME` should work in principle, but that is unverified. Open issue #7012 tracks writing file paths as `asset`-typed parameters, which resolvers depend on ([issue #7012](https://github.com/GafferHQ/gaffer/issues/7012)). Per-face GeomSubset material assignments were reported broken through SceneReader in December 2024 ([gaffer-dev](https://groups.google.com/g/gaffer-dev/c/wMGduLaghKI)).

The version direction is favourable. The local check shows Gaffer 1.7.7 bundles **USD 26.05**, while Maya 2027 on this machine runs **mayaUsd 0.37.0 on USD 25.11**. So Maya-written publishes are read by a newer USD, which is the safe direction. Gaffer-written layers going back into Maya go from newer to older, which is usually fine for plain `.usd`/`.usda` but is a risk for newer schemas such as Gaussian-splat prims. Since 1.7, Gaffer also writes OSL shaders and `ri:` attributes in hdPrman-conformant form by default (`IECOREUSD_WRITE_CONFORMANT_*`), and since 1.4.x it writes Windows asset paths with forward slashes ([Changes.md](https://github.com/GafferHQ/gaffer/blob/main/Changes.md)). Neither SceneReader's support for `.usdz` nor its `metersPerUnit` handling from Maya's centimetre scenes was confirmed. Both matter because the pipe publishes `.usd` and `.usdz`.

On the Maya side there is **no plug-in and no live link**. Cortex 10.6 removed all DCC integrations, IECoreMaya included ([Cortex PR #1504](https://github.com/ImageEngine/cortex/pull/1504)). Gaffer 1.7.0 also removed built-in GLWidget hosting inside Maya and Houdini ([Changes.md](https://github.com/GafferHQ/gaffer/blob/main/Changes.md)). The handoff is files. The best-documented production case matches RMIT's data exactly. Maya assets were exported as Arnold USD with lookdev and arrived in Gaffer as `ai:surface` attributes that ShaderTweaks could edit. Shot animation came in as Alembic. Haddon recommended **CopyAttributes** to move `ai:surface` from the USD stream onto the Alembic geometry, and the user found that MergeScenes in Attributes "Merge" mode also worked ([gaffer-dev, 2022](https://groups.google.com/g/gaffer-dev/c/tH7kPSDT8DQ)). Both rely on **identical location paths in the USD model and the Alembic cache**. That makes the pipe's `asset_model_GRP > geo > render/proxy` hierarchy and `<asset>_<part>_GEO` naming a hard contract rather than a convention. The reverse direction has more friction. Maya's Arnold ignored subdivision on a Gaffer-exported USD until the Arnold primvars were added, and the suggested fix was a ShuffleAttributes rename before export ([gaffer-dev](https://groups.google.com/g/gaffer-dev/c/WdUWFUdgeFA)). The underlying `primvars:arnold:*` versus `ai:*` naming split is still an open issue ([#4471](https://github.com/GafferHQ/gaffer/issues/4471)). Round-trips are still being hardened: 1.7.6 fixed Arnold OSL ramps that broke after USD export and re-import ([Digital Production](https://digitalproduction.com/2026/11/10/gaffer-1-7-6-painting-lighting-and-mcp/)). Treat Gaffer as a destination for lookdev and lighting, not as a round-trip editor. MaterialX authored in Maya's LookdevX is untested in Gaffer and should not be the bridge. Arnold-native networks such as standard_surface, or UsdPreviewSurface, are safer.

## Arnold matches on paper; the SDK layout and the licence are the real gates

Gaffer chooses its Arnold module at launch. It reads `ARNOLD_ROOT/include/ai_version.h`, takes the ARCH.MAJOR number (for example 7.5), loads `arnold/7.5`, and puts Arnold's `bin`, `python`, `plugins` and usdArnold resources on the relevant paths. It also turns off Autodesk's ADP analytics unless the studio opts in ([_gaffer.py](https://github.com/GafferHQ/gaffer/blob/main/bin/__private/_gaffer.py)). The 1.7.7.0 CI builds against Arnold 7.4.1.0 and 7.5.1.0 ([main.yml @1.7.7.0](https://github.com/GafferHQ/gaffer/blob/1.7.7.0/.github/workflows/main.yml)), and the download page states minimums of **7.4.1.0 and 7.5.1.0** ([download page](https://www.gafferhq.org/download/)). The web sources disagree with this machine on what Maya 2027 ships. Autodesk's What's New says Maya 2027.0 shipped **MtoA 5.6.0 with Arnold 7.5.0.0** ([Autodesk](https://help.autodesk.com/cloudhelp/2027/ENU/Maya-WhatsNew/files/GUID-82D13118-E987-4B5E-B1DA-C2A01F51058C.htm)). That would be *below* Gaffer's 7.5.1.0 floor, and the research notes inferred that labs would therefore need a Maya point update. Third-party coverage places Arnold 7.5.2 with MtoA 5.6.2 and MtoA 5.6.4 with Maya 2027.3 ([CG Channel](https://www.cgchannel.com/2026/07/maya-2027-2-lets-you-train-your-own-ai-animation-models/); [CG Channel](https://www.cgchannel.com/?p=180356)). **The local check settles it for this machine.** The installed MtoA's `ai_version.h` reads **Arnold 7.5.2.0**. That clears the 7.5.1.0 floor and also meets the 7.5.2 requirement for Gaussian-splat rendering in Gaffer 1.7.4+ ([Changes.md](https://github.com/GafferHQ/gaffer/blob/main/Changes.md)). Lab images built from an older Maya 2027.0 install would not clear the floor, so every lab image needs the same check.

The local inspection also found a probable trap. MtoA keeps its header at `include\arnold\ai_version.h`, but Gaffer looks for `include\ai_version.h`, the layout of the standalone Arnold SDK. Pointing `ARNOLD_ROOT` at `C:\Program Files\Autodesk\Arnold\maya2027` will therefore probably fail the check with "GafferArnold extension not available". The plan should assume a **standalone Arnold SDK 7.5.x installed per lab machine, at the same point version as MtoA** (7.5.2.0 here). Matching the point version keeps shader parameter sets consistent: changes like 7.5.2's `driver_exr` change ripple into both apps. It also matters for licensing, because Autodesk says jobs share a licence only when they run the same Arnold version ([Arnold Licensing](https://help.autodesk.com/cloudhelp/ENU/AR-Core/files/arnold-setup/arnold_user_guide_arnold_setup_ac_licensing_home_html.html)). This has not been tested and needs a hand test before anything is built on it.

Licensing is the least certain part of the plan. Autodesk's licensing page says schools get free **network (NLM) licences**, that every render node needs one, and that unlicensed renders are watermarked. It also notes that MtoA allows watermark-free interactive rendering inside Maya without a licence, while Houdini, Katana and Cinema 4D need a licence even to remove the IPR watermark ([Arnold Licensing](https://help.autodesk.com/cloudhelp/ENU/AR-Core/files/arnold-setup/arnold_user_guide_arnold_setup_ac_licensing_home_html.html)). Arnold has been free to schools since 2017 ([CG Channel 2017](https://www.cgchannel.com/2017/08/autodesk-makes-arnold-free-to-schools-and-colleges)). Gaffer calls Arnold core directly, so **Gaffer's interactive Viewer renders will most likely watermark without a licence**, unlike Maya's RenderView. Gaffer's own CI renders unlicensed and watermarked on purpose, and Gaffer exposes `ai:abort_on_license_fail` so farm jobs fail instead of watermarking ([main.yml](https://github.com/GafferHQ/gaffer/blob/1.7.7.0/.github/workflows/main.yml); [Changes.md](https://github.com/GafferHQ/gaffer/blob/main/Changes.md)). No Autodesk or Gaffer document says whether RMIT's education NLM licences or students' Education Community named-user licences cover Arnold used from Gaffer. That has to go to Autodesk or RMIT's licence administrator before Gaffer goes in front of students.

## Python, configuration and Windows deployment

Gaffer runs its **own embedded CPython**. The local zip contains `python311.dll` and `boost_python311.dll`, while Maya 2027's mayapy reports 3.13.9. The two apps cannot share an interpreter or compiled wheels. Pure-Python pipe modules (pipeEnv-style path logic, shotgun_api3, the publish API's non-Maya parts) can be shared only if they avoid 3.12+/3.13 syntax and stdlib APIs until Gaffer's next major moves to 3.13. Anything importing `maya.cmds` obviously stays on the Maya side. Gaffer also sets `PYTHONNOUSERSITE=1`, prepends its own `python/` folder to `PYTHONPATH` and appends each extension's ([_gaffer.py](https://github.com/GafferHQ/gaffer/blob/main/bin/__private/_gaffer.py)). Extending Gaffer needs no compiler. A custom node is a `Gaffer.ComputeNode` subclass that overrides `affects`, `hash` and `compute` ([AddNode.py](https://github.com/GafferHQ/gaffer/blob/main/python/GafferTest/AddNode.py)). Boxes built in the UI can be exported to Python node classes with `ExtensionAlgo.exportNode()`. Simpler still, a Reference to a `.grf` file can be added to the node menu with its own name and icon ([Startup Config 3 tutorial](https://github.com/GafferHQ/gaffer/blob/main/doc/source/WorkingWithThePythonScriptingAPI/TutorialStartupConfig3/index.md)). Avoid C++ extensions: they need rebuilding with MSVC on every major version.

Configuration happens through Python **startup scripts**, one folder per app (`startup/gui`, `startup/dispatch` and so on), found on `GAFFER_STARTUP_PATHS`. The **`GAFFER_EXTENSION_PATHS`** variable bundles a whole extension root (python, startup, apps, graphics, OSL shaders) into one entry. Gaffer loads its own Arnold module the same way ([_gaffer.py](https://github.com/GafferHQ/gaffer/blob/main/bin/__private/_gaffer.py)). The documented recipe for studio variables adds read-only `project:*` context variables to every script. They are saved in the `.gfr`, so they travel with it to the farm ([Startup Config 1 tutorial](https://github.com/GafferHQ/gaffer/blob/main/doc/source/WorkingWithThePythonScriptingAPI/TutorialStartupConfig1/index.md)). In plug values, `${name}` expands **both context variables and environment variables** ([String Substitution Syntax](https://github.com/GafferHQ/gaffer/blob/main/doc/source/Reference/ScriptingReference/StringSubstitutionSyntax/index.md)), so `${PIPE_SCRATCH}/...` in a SceneReader plays the same role as the pipe's `$PIPE_SCRATCH` on Maya stage nodes. The stock config points `project:rootDirectory`, and with it the dispatcher job folders and texture bakes, at `$HOME/gaffer/projects/...` ([project.py](https://github.com/GafferHQ/gaffer/blob/main/startup/gui/project.py)). On lab machines that is the Windows user profile, so the pipe must override it. Two Windows details come from the docs rather than tests. First, **backslash is Gaffer's escape character**, so paths in plugs should use forward slashes (`G:/scratch/...`, `//server/share/...`). Second, since 1.1 a path starting with a single `/` or `\` and no drive letter is read as UNC ([Changes.md](https://github.com/GafferHQ/gaffer/blob/main/Changes.md)). Mapped-drive versus UNC equivalence, case-insensitive comparison and SharePoint/OneDrive placeholder files are all untested.

Installation is a portable directory with no installer. The 1.7.7.0 zip is **472 MB compressed, 1.65 GB and 51,510 files unpacked**, according to the local check. It needs the MSVC++ redistributable, and the vendor recommends an NVIDIA GPU ([Installing Gaffer](https://www.gafferhq.org/documentation/1.7.7.0/GettingStarted/InstallingGaffer/index.html); [download page](https://www.gafferhq.org/download/)). `bin\gaffer.cmd` sets `HOME` from `USERPROFILE`, so per-user preferences land in `%USERPROFILE%\gaffer`. It also sets `PXR_USD_WINDOWS_DLL_PATH` to stop Gaffer's USD clashing with other USD installs on `PATH` ([gaffer.cmd](https://github.com/GafferHQ/gaffer/blob/main/bin/gaffer.cmd)). Windows has had official builds since **1.2.0.0 (February 2023)**. It has matured through MSVC 2022 builds, a TBB allocator that gave "significantly better performance" in 1.5, and a steady stream of path and environment fixes, including one where environment variable names were upper-cased ([Changes.md](https://github.com/GafferHQ/gaffer/blob/main/Changes.md)). Field reports include a Windows 11 launch failure fixed in 1.5.1 ([gaffer-dev](https://groups.google.com/g/gaffer-dev/c/G7GIpAVD3nU)) and an unresolved UI-slowdown thread ([gaffer-dev](https://groups.google.com/g/gaffer-dev/c/JYIUdb0G-oU)). Most reported production setups run on Linux. Extracting a versioned folder locally on each lab image will almost certainly outperform running 51,000 files off a UNC share.

## Dispatch maps cleanly onto the Scout render service

GafferDispatch turns TaskNode dependencies into a tree of batches. Every dispatcher, official or custom, ends up running the same command: **`gaffer execute -script <file> -nodes <node> -frames <list> -context -<var> <value>`** ([TractorDispatcher.py](https://github.com/GafferHQ/gaffer/blob/main/python/GafferTractor/TractorDispatcher.py); [LocalDispatcher.py](https://github.com/GafferHQ/gaffer/blob/main/python/GafferDispatch/LocalDispatcher.py)). The official dispatchers are Local, Tractor and, new in 1.7, **Flamenco**. Wedge, TaskSwitch, PythonCommand, SystemCommand and the new 1.7 file tasks (FileList, CopyFiles, RenameFiles, DeleteFiles) are all pure Python ([Wedge.py](https://github.com/GafferHQ/gaffer/blob/main/python/GafferDispatch/Wedge.py); [Changes.md](https://github.com/GafferHQ/gaffer/blob/main/Changes.md)). TractorDispatcher is effectively a template for writing your own. It subclasses `GafferDispatch.Dispatcher`, implements `_doDispatch(rootBatch)`, walks `preTasks()` and de-duplicates diamond dependencies. It reads the saved script from the `dispatcher:scriptFileName` context entry and offers a `preSpoolSignal()` hook for studio changes before submission. A **pure-Python ScoutDispatcher** of a similar size, submitting each batch to the Scout render service queue with its dependency edges, is the natural integration. The render service can also call `gaffer execute` directly for one-off jobs. Deadline has the actively maintained community **GafferDeadline**, tested on Windows, last committed 2026-11-18 ([GafferDeadline](https://github.com/hypothetical-inc/GafferDeadline)). The OpenCue dispatcher has been stale since 2022 ([GafferOpenCue](https://github.com/boberfly/GafferOpenCue)).

Nothing off the shelf fits the pipe, but there are working examples to borrow from. **RVXStudio/ayon-gaffer** is used in production. It ships versioned Box `.gfr` pipeline nodes and a menu built from a startup script, and publishes through Deadline ([RVXStudio/ayon-gaffer](https://github.com/RVXStudio/ayon-gaffer)). **sosoyan/ayon-gaffer** switches task context inside one multi-shot script by rewriting script variables ([sosoyan/ayon-gaffer](https://github.com/sosoyan/ayon-gaffer)). The ShotGrid Toolkit engine **tk-gaffer** was tested only on Gaffer 0.59, has "not been used in production", and was last touched in 2021 ([tk-gaffer](https://github.com/diegogarciahuerta/tk-gaffer)). ShotGrid integration is better done as pipe Python (shotgun_api3 runs under 3.11) called from a PythonCommand task or a dispatch hook. One new route matters for development. The local zip contains **`gaffer mcp`** (added in 1.7.5), an MCP server that lets coding agents drive a headless Gaffer. Its own help text suggests `claude mcp add gaffer-headless -- gaffer mcp` and warns that it "gives clients full control over Gaffer, and anything else that can be done with Python" ([Changes.md](https://github.com/GafferHQ/gaffer/blob/main/Changes.md)). That makes it a fast way for pipeline developers using Claude Code to build and check graphs. It should be a developer tool, never something enabled on student machines.

## Small expert community, no school precedent, a Katana-shaped skill

Public adoption is concentrated in the Cinesite group: Image Engine, Cinesite VFX and Animation, and Trixter, which made the best public training videos ([Cinesite](https://cinesite.com/technology/); [Image Engine](https://image-engine.com/insight/technology-at-image-engine)). Outside the group there are only scattered users, such as Whiskytree, which ran its own Deadline plugin ([Thinkbox forum](https://forums.thinkboxsoftware.com/t/gaffer-support/13511)). **No school or university case study was found.** Learning material is reference-heavy: official docs, a handful of tutorials (GafferBot, Spreadsheets, Light Linking, Camera), user-group recordings on Vimeo and the GafferHQ blog ([gafferhq.org/resources](https://www.gafferhq.org/resources/)). The strongest video courses are Trixter's Basics and Intermediate series and Arvid Schneider's Gaffer + Arnold videos, all from 2024 and therefore older than the 1.7 UI ([Trixter Basics](https://www.youtube.com/watch?v=qJWtai73TB8); [Arvid Schneider](https://www.youtube.com/watch?v=lAgBcOFMf5k)). The community is small but expert. Haddon answered a 2022 shader question the same day and merged a fix three days after a bug report ([gaffer-dev](https://groups.google.com/g/gaffer-dev/c/tH7kPSDT8DQ)). There is also a community Discord, GitHub Discussions and a forum on We Suck Less ([resources](https://www.gafferhq.org/resources/)).

The comparison with the alternatives comes down to which skill each one teaches. Gaffer and **Katana** share a paradigm: a procedural scene graph, filtered locations, inherited attributes and context-driven variation. Katana costs money per faculty seat and is node-locked for students through Foundry's Education Collective, and Foundry's own pages quote conflicting prices ([Foundry Education](https://www.foundry.com/education); [Foundry FAQ](https://www.foundry.com/education/faqs)). **Houdini Solaris** costs about $95 a year per student with Karma included ([SideFX](https://www.sidefx.com/education/education-programs/students/)). It teaches USD-native composition (layers, variants, LOPs), which maps more directly onto a USD-publishing pipe, but it adds a whole new DCC. Commentary from 2026 calls Gaffer the closest open-source Katana equivalent, with adoption limited mostly to the Cinesite group ([cglounge.studio](https://cglounge.studio/journal/the-honest-map-to-dcc-software)). Those are low-authority opinion pieces, not data. Gaffer's honest position is this: it teaches the Katana skill set for free, and it suits graduates heading to Cinesite-group studios, but it is weaker than Solaris at teaching USD composition itself.

## What this means for the RMIT pipe, and what has to be tested first

Gaffer's clearest fit is a **Lighting/LookDev stage that reads published model USD and Alembic shot caches, layers lookdev and lighting procedurally, and dispatches through the Scout render service**. Its project variables can map onto the pipe's `pipe:root`/show/asset/shot. It would be packaged as one pure-Python extension folder (python, `startup/gui`, `startup/dispatch`, graphics) on `GAFFER_EXTENSION_PATHS`, set by a launcher that also sets `ARNOLD_ROOT`, the OCIO config and `PIPE_SCRATCH`. The pipe's existing rules carry over well. Relative USD paths and `${PIPE_SCRATCH}` already survive drive moves. Refusing off-pipe scenes becomes a startup check, and a fixed department list maps onto bookmarks and menus. Each of the items below should be resolved before anything is built on it.

| Open question | Why it matters | How to settle it |
|---|---|---|
| Can MtoA's folder serve as `ARNOLD_ROOT`, or is the standalone 7.5.2.0 SDK required? | Header path mismatch (`include\arnold\` vs `include\`) probably blocks GafferArnold | Launch Gaffer with each `ARNOLD_ROOT` and read the startup warning |
| Does RMIT's education NLM licence cover Arnold driven from Gaffer, including Viewer IPR? | Gaffer's IPR probably watermarks without a licence, unlike Maya's | Ask Autodesk or the licence admin; test with the command-line licence manager |
| Do Gaffer and MtoA renders match? | Same Arnold point version, OCIO config/view and colour manager | Render one published asset in both and diff the EXRs |
| Do the model `.usd`/`.usdz`, `metersPerUnit`, purposes and render/proxy groups read correctly? | SceneReader `.usdz` and unit handling are unconfirmed | Load a real mpModel publish in SceneReader |
| Does lookdev transfer to Alembic caches by path (CopyAttributes / MergeScenes)? | Needs identical hierarchy between the USD publish and the Maya Alembic export | Build one shot from a published rig cache and model |
| Variants, payloads, nested references from Maya layout | Composition is flattened; variant control is undocumented | Test against the pending Component Creator / variant decision |
| Which shared pipe modules must stay 3.11-safe? | Gaffer 3.11 vs Maya 3.13.9 | Import pipeEnv and shotgun_api3 under `gaffer python`; add a 3.11 check to the test run |
| Gaffer-to-Maya overlay via USDLayerWriter | `ai:*` vs `primvars:arnold:*` naming; USD 26.05 → 25.11 downgrade | Write a lookdev layer and compose it in mayaUsd |
| Local install vs running from H (T7 / SharePoint / UNC) | 51k files and 1.65 GB; forward slashes; untested UNC/SharePoint behaviour | Time launches both ways; keep the install local and the config on H |
| Which major to pin for the March 2027 intake? | Next major moves to Python 3.13 / Qt 6.8 and carries breaking changes | Pin 1.7.x for the year; evaluate 1.8 in the off-season |

## Conclusion

The research points to a staged decision, not a yes or no. Gaffer's technical shape is right for a pipe that already treats Maya as an authoring tool and USD and Alembic as the contract between departments. Its procedural "read then tweak" model enforces the pipe's rule that published assets are never edited in place, more strictly than Maya Render Setup ever could. The risks sit at the edges where Gaffer meets things RMIT doesn't control: Autodesk's licensing terms for a third-party Arnold host, the standalone SDK layout, and Windows file-share behaviour. The two cheapest tests clear most of the uncertainty: launching Gaffer against the MtoA folder and the standalone SDK, and asking about the licence. The bundled Cycles is a sound fallback that keeps teaching going if Arnold licensing stalls.

One finding goes against the obvious assumption. Python parity was expected to get easier over time, but for this pipe it currently runs backwards: Maya 2027 is ahead on 3.13 and Gaffer 1.7 is behind on 3.11. Gaffer's next major only converges when it ships. Until then, "write shared pipe code to the older interpreter" is a constraint that a test can enforce. Separately, `gaffer mcp` changes the cost of building the integration. Graphs, dispatchers and startup configs can be developed and checked by a coding agent against a headless Gaffer. That makes a pilot (one asset, one shot, one ScoutDispatcher) realistic within the dev period before the March 2027 intake.
