# mpToolSet Dev Notes

## ngSkinTools2 — moved to a separate installer (resolved 2026-07-16)

**Old problem:** ngSkinTools2 installed automatically as part of the main `install.py`, which caused two recurring issues: Maya's Maya 2025 "untrusted folder" warning (the old `_patch_usersetup` `ngskin_block` manually set `MAYA_PLUG_IN_PATH` and called `loadPlugin('ngSkinTools2')`, which Maya 2025's plugin trust system flags for non-hardcoded locations), and locked-file install failures — reinstalling/updating mpToolSet while ngSkinTools2 was loaded would block on `shutil.rmtree` of the `ApplicationPlugins` folder.

**Fix:** ngSkinTools2 is no longer touched by the main `install.py`/`uninstall.py` at all. It now lives in its own top-level folder, `mpToolSet/ngSkinTools2/`, with its own self-contained `install.py`/`uninstall.py` that students drag in separately, only when they need it. It relies purely on Maya's native `ApplicationPlugins`/`PackageContents.xml` auto-discovery — no `userSetup.py` changes, no `MAYA_PLUG_IN_PATH` hack — which also sidesteps the untrusted-folder warning. Decoupling it from the main installer's manifest/backup system means updating mpRig/mpAnim tools can no longer be blocked by a locked ngSkinTools2 file, and vice versa.

## Studio Library — moved to a separate installer (resolved 2026-07-21)

**Old problem:** Studio Library (`mutils`, `studiolibrary`, `studiolibrarymaya`, `studioqt`, `studiovendor`) was copied by the main `install.py` on every install/reinstall via `shutil.rmtree` + `shutil.copytree`. Reinstalling/updating mpToolSet while Studio Library was open (or otherwise loaded) in the running Maya session hit the same class of bug as the old ngSkinTools2 problem: `rmtree` raised `PermissionError: [WinError 5] Access is denied` on a locked file (observed on `mutils/gui/__pycache__`), which aborted `_install()` partway through, left the package half-deleted on disk, and — because the studio-library copy loop ran *before* the shelf-build step for that shelf dir — also silently skipped building the shelf. A partially-deleted Studio Library then errored/repainted repeatedly on subsequent Maya launches, severe enough in one case to require deleting Maya prefs entirely to recover.

**Fix:** Two changes, one in each toolset's `install.py`. First, `_copy_tree`'s `rmtree`-then-`copytree` was replaced everywhere it's used (including `shelfDev/mpInstaller.py`, the dev installer) with a merge-copy (`shutil.copytree(src, dst, dirs_exist_ok=True)`) — this never deletes the live destination at all, so it can't hit the Windows lock in the first place. Second, and more structurally, Studio Library was pulled out of the main installer entirely, the same way ngSkinTools2 was: it now lives in its own top-level folder, `mpToolSet/studioLibrary/` and `studio4AnimToolset/studioLibrary/`, each with a self-contained `install.py`/`uninstall.py` that deploys the five packages flat into Maya's scripts folder. Studio Library rarely changes, but the main installer gets rerun often (every tool update), so decoupling means it's only touched when a student explicitly chooses to install/update it — not on every routine reinstall.

Side note: `studio4AnimToolset/install.py`'s old Studio Library copy nested the whole `studiolibrary/` source folder one level too deep (`scripts/studiolibrary/mutils/...` instead of `scripts/mutils/...`), which likely meant `import studiolibrary` never actually resolved correctly for studio4Anim students even before this bug. The new per-toolset `studioLibrary/install.py` deploys flat like mpToolSet always did, fixing that as a side effect.
